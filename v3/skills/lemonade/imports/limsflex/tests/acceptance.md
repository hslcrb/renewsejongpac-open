# limsflex 수용 시나리오

작업에 해당하는 시나리오를 선택해 실제 결과를 확인한다. 아래 항목은 결과의 관찰 기준이며, 문서에 규칙이 적혀 있다는 사실만으로 통과한 것으로 보지 않는다.

## 1. 표현이 풍부한 새 화면

요청: 강한 색상, 큰 타이포그래피, 겹치는 장식, 모션을 가진 반응형 랜딩 페이지를 만든다.

기대 결과: 요청한 표현을 구현하며 플레인 스타일·특정 브랜드 색상·고정 모바일 폭으로 축소하지 않는다. 본문은 문서 흐름과 Flexbox/Grid로 구성하고, 장식은 읽기·포커스 순서를 방해하지 않는다. 모션 감소 설정에서도 내용을 이용할 수 있다.

## 2. 프로젝트에 기본 CSS가 없음

요청: 새 폴더에 완전한 HTML 화면을 만든다.

기대 결과: 제공 기본 CSS를 실제 프로젝트에 복사하거나 적합한 기본 CSS를 작성한다. HTML의 실제 위치에서 링크가 해석되고 기본 CSS가 페이지 CSS보다 먼저 적용된다. 폼·키보드 포커스·미디어·숨김 처리에 필요한 기반을 빠뜨리지 않는다.

## 3. 기본 CSS를 직접 설계해야 함

요청: 기존 reset이 커스텀 폼이나 디자인과 충돌하므로 화면에 맞는 기본 CSS를 만든다.

기대 결과: 제공 파일을 고정 계약처럼 강제하지 않는다. 필요한 reset을 직접 만들고, 네이티브 checkbox/radio와 포커스를 보존한다. 공유 파일 변경이 요청 범위 밖에 영향을 주면 범위에 맞는 별도 기반을 사용한다.

## 4. 코드 모양이 흐트러진 초안

상황: 새 코드에 2칸 들여쓰기, 탭, camelCase/BEM 클래스, 한 줄짜리 CSS 선언 묶음이 섞여 있다.

기대 결과: 작업 범위의 코드를 4칸 들여쓰기와 kebab-case, 한 줄당 CSS 선언 하나로 정리한다. `<style>` 최상위 선택자는 첫 칸, 미디어쿼리의 선택자는 4칸, 선언은 8칸이다. 외부 클래스·기존 공용 helper·무관한 파일을 깨뜨리며 이름을 바꾸지 않는다.

## 5. 긴 콘텐츠와 좁은 화면

상황: flex 카드에 긴 제목·URL·번역문을 넣고 좁은 화면 및 확대에서 확인한다.

기대 결과: 내용에 맞는 최소 크기·줄바꿈·wrap을 설정하고, 필요하면 특정 영역에 스크롤을 제공한다. 전역 overflow 차단으로 손실을 숨기지 않는다. DOM 읽기·Tab 순서를 유지한다.

## 6. 폼과 아이콘 조작

상황: 아이콘 버튼, 입력 필드, 체크 상태, 오류, 비활성 CTA를 구현한다.

기대 결과: 실제 button/input과 연관된 레이블·접근 가능한 이름·오류 정보를 사용한다. 버튼 타입과 disabled 동작이 맞고, 키보드로 필요한 조작을 할 수 있으며 포커스가 보인다. 상태 목록을 장식 아이콘 때문에 checkbox로 바꾸지 않는다.

## 7. 기존 프로젝트 또는 명시적 출력 형식

요청: 기존 컴포넌트를 수정하거나 HTML만/별도 CSS를 명시한다.

기대 결과: 기존 구조와 명시한 출력 형식을 지키며 기술스택을 임의로 바꾸지 않는다. 스타일을 구현하는 경우 적합한 기존 공용 기본 CSS를 재사용하고 중복 reset이나 존재하지 않는 링크를 추가하지 않는다.

## 8. 관련 그룹과 공유 가능한 fragment 링크

요청: 주요 기능과 안내 등 관련 콘텐츠를 묶고 각 그룹의 URL을 직접 공유할 수 있게 한다.

기대 결과: 콘텐츠에 맞는 컨테이너와 안정적이고 고유한 kebab-case ID를 사용한다. 실제 `href="#group-id"` 앵커가 URL을 갱신하고, 직접 진입·새로고침·뒤로/앞으로 이동이 올바른 대상을 보여 준다. 고정 헤더에 대상이 가려지지 않고, 시각적 래퍼를 무조건 section으로 바꾸거나 반복 그룹의 ID·기존 label/ARIA 연결을 중복·파괴하지 않는다.
