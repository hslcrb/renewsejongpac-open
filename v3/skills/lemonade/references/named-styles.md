# Named styles: translate the visual grammar

Use this route when a user requests a recognizable reference site's feel, including "Toss style" or "Sejong Center style." Read the matching profile, then apply it to the user's subject and visitor task. These are conditional reference directions inside `$lemonade`, not additional skills or global defaults.

| Request aliases | Read | Primary character |
| --- | --- | --- |
| Toss, toss.im, 토스 | [Toss profile](style-toss.md) | Spacious product storytelling, large plain-language statements, contextual media and focused demonstrations |
| Sejong Center, Sejong Cultural Center, SejongPAC, 세종문화회관 | [Sejong profile](style-sejong.md) | Editorial rules and grids, poster-led discovery, expressive scale and dense but comparable program information |

The names identify reference sources; they are not names for the customer's product. Keep maintained guidance in English and use the user's requested language in the deliverable.

## Apply a profile

1. **Resolve the scope.** Keep the customer's brand, information architecture, assets and working behavior unless the request changes them. A code-formatting or standards-only task still follows [code-and-markup.md](code-and-markup.md) without a visual redesign. A named style does not imply permission to rewrite unrelated screens.
2. **Select the relevant grammar.** Choose observed relationships between type, space, imagery, grouping, information density and interaction. State which profile traits serve this task. Separate archive observations from your proposed tokens and unverified behavior.
3. **Compose an original response.** Write the customer's own content; create a task-specific hierarchy and section progression; use owned, commissioned, generated or appropriately licensed assets. Reuse principles such as a generous explanation-to-demonstration relationship or a ruled program grid. Design the actual focal composition, illustration, copy and interaction sequence for the new subject.
4. **Implement for the actual platform.** Establish project-owned tokens, semantic components, responsive changes and state contracts. Select dimensions from the content and available space. Archived numbers below are evidence, not mandatory tokens. Retain native behavior, accessible focus and readable content when motion or media fails.
5. **Review resemblance and independence.** Check the intended atmosphere at whole-page and component scale, while checking that the result has its own content, layout decisions and assets. Explain both the transferred principles and the independent decisions in a short handoff. Run the relevant [behavioral scenarios](../evals/named-style-evals.json) when updating these profiles.

A useful internal design brief is:

```text
Requested reference / current task and constraints
Observed principles selected / why they help this task
Original hierarchy, copy, assets and composition decisions
Proposed type, space, color and component relationships
Responsive and interaction changes / checks and evidence limits
```

This is a decision aid, not a requirement to send a long report before doing the work. Proceed with reasonable assumptions when the brief is clear.

## Keep the new identity coherent

Source logos, slogans, photographs, poster art, app screens, custom illustrations, fonts and downloaded code are not a reusable starter kit. Inspect archive assets as evidence; obtain independently suitable output assets and verify their rights. Changing a logo or a color does not create a new composition. Derive the layout from the new content instead of tracing the source screen or reproducing its distinctive sequence of reveals.

If an existing palette is fixed, translate spacing, hierarchy and grouping within that palette. For a dense application requested in Toss style, retain data density and task controls; the archived marketing homepage is not evidence for Toss's transaction or dashboard UI. For a small single-event page requested in Sejong style, use appropriate poster hierarchy and editorial rules without inventing a venue portal, calendar or institutional services.

If both names are requested, assign them roles explicitly: for example, one can inform program discovery while the other informs an explanatory service panel. Use one coherent type, spacing and state system. Resolve conflicting hierarchy from the primary visitor task instead of mixing every signature.

If the user supplies a different screenshot or asks for the current site, inspect that evidence and update the direction; these profiles describe the supplied archive only. For an unfamiliar named site, inspect available sources rather than silently substituting one of these two profiles. When access is unavailable, state the uncertainty and provide a provisional, task-based direction.

## Evidence boundaries

Both profiles were reviewed on 2026-10-15 from user-supplied Specialitye exports. The export manifests contain no capture date. A review date is not a capture date or a claim about the current live site. The profiles and their source locators are bundled with the skill; the original archives and local captures are not required for use and may be absent from an installed copy.

Keep four categories distinct: first-party source declarations; rendered observations in a specified local viewport/state; design inferences; and new implementation proposals. Asset frame sequences show candidate imagery, not verified live animation or timing. Captured third-party pages, exporter patches, missing requests and incomplete animation states are not the named site's visual contract. Report a broken local render as a limitation and design a usable fallback rather than reproducing the breakage.
