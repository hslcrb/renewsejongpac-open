# 근거로 강화하는 반복 절차

실제 실패와 더 나은 설명이 생겼을 때 스킬을 갱신한다. 수집량과 금지 항목 수를 품질로 간주하지 않는다.
요청 범위 안에서 실행한다. 별도 요청 없이 무기한 실행·스케줄·외부 연결을 만들지 않는다.

1. **실패를 구체화한다.** 예: 공연명 잘림, 상태 누락, 한글 겹침, 달력이 장식 카드로 분류됨.
   현재 스킬을 사용한 독립 평가의 결정을 기록한다. 바뀐 문장만 검사하는 것은 행동 검증이 아니다.
2. **역할에 맞는 근거를 찾는다.** [GDWEB](https://www.gdweb.co.kr/main/)의 업종·표현·콘셉트로 후보를 좁히고
   상세 선정작과 원 사이트에 직접 접속한다. 관련 업종, 다른 업종의 같은 과업, 대조 사례를 비교한다.
   판단이 설명되면 수집을 멈춘다. 보드·정적 캡처·원 사이트 텍스트·브라우저 조작은 다른 증거다.
3. **적용 조건을 쓴다.** 관찰 → 돕는 과업 → 적용/제외 조건 → 실제 검증 순으로 정리한다.
   같은 포스터 카드는 비교에 도움이 된다. 이것이 모든 페이지를 카드로 만들거나 모든 카드를 금지할 근거는 아니다.
4. **독립 재평가한다.** 기대 정답 없이 실제 요청·스킬·최소 원본을 전달한다. 공연장·기관·단일 행동 랜딩·기존 브랜드·긴 한글을 다룬다.
   콘텐츠/행동 보존, 출처가 선택에 미친 영향, 모바일 과업, 미확인 표시를 평가한다.
   좁은 검사부터 하고 마지막에 통합 검사를 한 번 한다. 같은 수정이 두 번 실패하면 배운 점을 보고한다.
5. **정리한다.** 날짜·변경·평가·제한을 기록하고 중복 사례·출처 없는 데이터·효과 없는 규칙을 정리한다.
   공통 기준은 `principles.md`, 절차는 reference, 관찰 사례는 `reference-cases.json`에 둔다.

사례 기록:

```text
id / source URL / original URL / checked date
evidence kind / image size or viewport / inspected regions
visitor task / required fields / composition / visible controls
direct observation / inference / unverified behavior
adopted decision / counterexample / limits / asset rights
```

접속 거부·빈 클라이언트 렌더·도구 오류는 실제 상태로 남긴다. 성공하지 않은 접속을 라이브 검증으로 표현하지 않는다.
정적 자료의 가격·날짜는 현재 사실의 소스로 재사용하지 않는다. 참조 캡처의 재배포 권리를 추정하지 않는다.
기존 연구 247개, 번들 181개, 이번 GDWEB 정적 검토 12개는 별도다. 전환율 분석이나 247개 재검증으로 표현하지 않는다.
스킬에 자동 Git 갱신이나 리모트 재연결을 넣지 않는다.

## 직접 만든 결과에서 배우기

외부 갤러리의 정적 관찰은 `cases`, 직접 구현하고 검토한 결과는 `builds`에 따로 기록한다.
각 구현 사례에는 설계·출처·검증 문서 경로, 원본/미리보기, 검사 프로필과 너비, 확인한 상태와 입력 방식,
발견한 문제·수정·한계, 채택/제외 조건을 둔다. 예제가 패키지에 없으면 그 사실을 표시한다.
현재 CLI의 `source.available`은 구현 디렉터리와 검증 문서 경로가 존재한다는 뜻이다. 다른 자산·보고서의 존재나 실행 성공은 확인하지 않는다.
역할로 다시 찾을 수 있어야 하지만, 예제의 색상·글꼴·주제·이미지 수를 새로운 기본 템플릿으로 만들지 않는다.

온실 사례에서 문서화된 수정을 자동 검출과 구분한다. 이미지 높이와 태블릿 본문 크기를 구현 검토 중 고쳤다는 기록은 있지만,
최초 실패 보고서·캡처를 보존하지 않았다. 최종 PASS 보고서만으로
최초 결함이나 어떤 검사에서 검출했는지 증명할 수 없다. 없는 실패 캡처를 사후에 만들어 당시 증거처럼 쓰지 않는다.

다음부터 수정 전 보고서와 해당 화면을 따로 보관한다. 예: `.lemonade/inspect/before/`, `.lemonade/inspect/after/`.
검사 항목 수보다 무엇을 어떤 상태·너비·입력으로 확인했는지가 중요하다. 프로그램으로 date/select 값을 바꾼 검사는
상태 로직 확인이며 실제 키보드 조작 전체를 뜻하지 않는다. 직접 시각 검토·추가 독립 검토도 별도 기록한다.
테스트는 예상 항목과 값을 렌더의 구조와 독립적으로 정의한다. 같은 DOM에서 정답을 만들어 비교하면 잘못된 목록도 통과할 수 있다.
